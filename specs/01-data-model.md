## Task queue

### `tasks`
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| type | enum `task_type` | `investigate_alert`; V2: `extract_invoice` |
| payload | jsonb not null | `{ "alertId": "…" }` or `{ "invoiceId": "…" }` |
| status | enum `task_status` | `pending`, `in_progress`, `done`, `failed` |
| attempts | int not null default 0 | incremented on every claim |
| max_attempts | int not null default 3 | |
| available_at | timestamptz not null default now() | the task can only be claimed from this instant on (detector debounce) |
| locked_until | timestamptz null | |
| locked_by | text null | worker id |
| last_error | text null | |
| created_at, updated_at | timestamptz | |

Partial index: `(type, created_at) where status in ('pending', 'in_progress')`.

Claim query (in a transaction):

```sql
UPDATE tasks
SET status = 'in_progress', attempts = attempts + 1,
    locked_until = now() + interval '5 minutes', locked_by = $2, updated_at = now()
WHERE id = (
  SELECT id FROM tasks
  WHERE type = $1
    AND available_at <= now()
    AND (status = 'pending' OR (status = 'in_progress' AND locked_until < now()))
    AND attempts < max_attempts
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

An `in_progress` task whose lock has expired and whose `attempts >= max_attempts` moves to `failed` (sweep by the API every 30 s); the related alert moves to `escalated`.

## Full reset
`POST /admin/wipe` empties **all** tables (`TRUNCATE … CASCADE`): reference data, history, demo week, alerts, investigations, steps, reviews, tasks and (V2) invoices. Called by the simulator on every "Start" and "Reset": every simulation starts from an empty database. The simulation state is not stored in the database (see `04-simulator.md`).
